# INV-JJ-GITHUB-CHECKPOINT-01: coherent, verified checkpoints

Each small, coherent engineering or documentation unit must have a durable, described Jujutsu checkpoint and a verified push to its designated GitHub review branch. Checkpoint as work progresses, before handing off the unit, resetting context, or reporting it complete. A coherent unit has one reviewable purpose; arbitrary line counts and individual keystrokes do not define that boundary.

Jujutsu automatically snapshots the local working copy. That does not establish a remote checkpoint. Preserve the described commit and continue later edits in a successor change. Identify the task, owner, repository, branch, base, commit, changed scope and actual verification status. Read back the remote ref and require an exact match before reporting a successful GitHub check-in.

Publish source and deliberately selected repository documentation to the approved destination. Keep credentials, private planning and evidence packets, execution logs, databases, session material, build outputs and unrelated work out of a public source push. Use an owned review branch and preserve other writers' history.

Run the meaningful checks admitted for the unit. Label work in progress, failing checks and pending reviews honestly. Checkpointing does not replenish compiler or model budgets, authorize skipped proof, or require a full final suite after every edit. Required independent QA, adversarial review, technical acceptance and task completion retain their gates. Merge, release and deployment retain their separate authority.

When publication is unavailable, preserve the local checkpoint, record the concrete failure and accountable publication owner, and continue independent admitted work. Keep remote sync pending until verified. Do not blindly retry an uncertain push, force-update shared history, repair authentication or widen publication scope.

At a handoff, the receiver checks the immutable checkpoint, remote-ref receipt and verification status. Review evidence must name the revision it actually examined; subsequent source changes require applicable revalidation.

This document defines a workflow policy. It does not claim automatic runtime enforcement. A future agent pair-programming workflow can enforce the same boundary through checkpoint, publication, CI and review events without equating publication with acceptance.
