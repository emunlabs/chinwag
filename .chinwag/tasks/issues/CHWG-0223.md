Build the customer-facing one-request review presentation layer for the local web app and CLI status views (`design-v2` §§ 0, 4.3, 8.1–8.2), enforcing zero workflow babysitting, strict untrusted-findings escaping, and progressive disclosure of technical receipts.

### Exact Scope & Deliverables
1. **One-Request Action & Same-ID Submission Persistence (§ 2.2, § 8.1):** Single **Request Review** action storing stable `client_intent_id` across lost acknowledgements (`Confirming request receipt`) and page closes/reopens, with zero model, reasoning, or token-cap controls exposed to users.
2. **Six Honest Plain-Language Card States (§ 8.1):**
   - `Preparing review` (including `Required checks are running` when `W_checks` is active; never claims model generation is running before `GENERATION_DISPATCHED`);
   - `Reviewing` (shown strictly once `GENERATION_DISPATCHED` commits);
   - `Review passed` (clearly framed as one valid review-gate check alongside other required workflow/QA gates, plus prominent `unreviewed_exempt_binary_paths` note when present);
   - `Changes requested` (file/line-anchored findings);
   - `Action needed on this change` (strictly for failing check assertions, oversized candidate split guidance, non-exempt binary artifacts, or concise domain-intent answers that auto-create the linked intent);
   - `Review did not complete — assigned to project operator` (distinguishing incident queued vs operator acknowledged, never claiming unresolved outcomes were cancelled or automatically repaired, and never asking users to run commands or re-request).
3. **Untrusted Findings Sanitization & Technical Receipt Drawer (§ 4.3, § 8.1):** Escape all model text as untrusted data (zero active HTML/script execution, zero runnable command buttons, zero external embedded media auto-fetches) and isolate raw hashes, internal state enums, seat handles, and token counters inside an expandable **Technical Receipt** drawer.
